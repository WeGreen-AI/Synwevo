# Docs 编辑安全与结果通知（CI-29）

第九节 9.8 里「项目与模板版本：至少避免多用户最后写入覆盖他人」「结果与复现：任务成功/部分失败/取消要有通知」
「项目组织与上下文：审批与目标副本可相互定位」三条的落地。三件事共用一个原则：服务端说了算，界面只是把服务端
已经知道的事说清楚。

## 1. 决策记录

| 项目 | 结论 |
|---|---|
| 问题与基线 | (a) 映射与模板早有修订校验（409 `stale` / `stale_template`），但项目设置——名称、样本规则、输出设置、模板选择——的 `PATCH /api/projects/{pid}` 没有任何版本检查：两个窗口（或两个人）各改一次，后到者静默覆盖先到者，界面上双方都看到「✓ 已自动保存」。(b) 通知目录（CI-22）定义了 `docs.job_finished` 与 `docs.file_rejected`，但 Docs 从未发出：`jobs` 表记录了申请人（`principal`），`source_files` 却不记录上传者，收件箱里没有任何 Docs 事件。(c) 经审批复制出的项目在目标空间打开时看不出它从哪里来、谁批准的（`origin=copy:<id>` 只是一列）。 |
| 成熟参考 | 乐观并发的标准形态：HTTP `If-Match`/ETag（RFC 9110 §13.1，同一语义在本仓库的映射保存 `base_rev` 已用多年）；Google Docs / Notion 的做法是实时合并，本项目没有可靠合并能力，按 9.8 的要求走「版本校验 + 编辑协调」，不冒充协同编辑。通知参考沿用 CI-22 的 Linear Inbox 模式（事件进收件箱、点击进对象、待办与已读分开）。 |
| 对比与选择 | (a) 以 `updated_at` 作为令牌：映射保存和模板改动也会推进它，同一人在同一窗口保存映射后再改规则会被误判为冲突，否决；以 `rev` 作为令牌：`rev` 是任务快照签名与复制摘要的一部分，改名也推进它会让副本申请无谓失效，否决；**新增 `settings_rev`（v14）**，只随名称/规则/输出/模板选择推进，`step`（导航状态）与归档不推进。调用方**自愿**带 `base_settings_rev`：界面总是带，机器客户端不带则保持旧行为（SDK 契约不变）。(b) 通知在完成事务的同一连接上写入（与状态一起落地或一起失败）；接收者只有发起任务的**登录用户**（机器身份无人可通知）；文件拒绝只通知上传者（新增 `source_files.created_by`）。(c) 项目详情附 `copied_from`（申请 id、源项目名、申请人、批准人、时间、是否自批、是否含来源），绝不含源空间 id 或文件。 |
| 预期变化 | 陈旧窗口保存规则/改名/换模板/改输出 → 409 `stale_project`，界面 toast「内容已在其他窗口或被其他人修改…已刷新为最新内容」并重载，对话框内显示原因；任务结束 → 发起人收件箱一条（标题含项目名与结果，正文含成功/失败份数，链接到任务页），每次运行只一条；文件被安全检查拒绝 → 上传者收件箱一条（立即邮件），链接到项目；副本页面顶部一行来源说明与「查看审批记录」链接（到账户服务组织页 `?approval=`）。 |
| 边界与风险 | 权限不变（通知只写给本来就能打开对象的人；`copied_from` 只给能打开副本的人）。schema v14 只加两列，默认值使旧行为不变。基础模式/机器上传：无上传者则不通知。SSE 消息流不涉及。三语言：Docs 外壳 6 条新字符串、服务端错误 1 条；通知标题/正文按读者语言渲染，`{outcome}` 按读者语言取词。移动端：来源说明是普通一行，收件箱是平台组件。 |
| 验收 | `apps/docs/tests/test_project_settings_rev.py`（陈旧 409 带当前修订、新鲜保存推进、`step` 不推进、非整数 400、不带令牌不检查、列表带修订）；`tests/integration/test_docs_notifications.py`（真实任务 → 一条 `docs.job_finished`，链接、计数、读者语言；扫描替身拒绝 → 一条 `docs.file_rejected`，同内容再传即拒且不重复通知，机器上传不通知）；`test_project_copy.py` 增 `copied_from` 断言；浏览器 `ui_e2e_docs_upgrades.py`（同一人两个标签页：陈旧保存被拒并重载、随后保存成功；任务结束后 Docs 内的平台铃铛显示结果并打开任务页）与 `ui_e2e_project_copy.py`（副本页来源行与审批链接）。 |
| 发布与恢复 | v14 两列可加可留；回滚到 v13 代码时列被忽略，无数据迁移。`PATCH` 新字段可选，SDK/CLI 不受影响。 |

## 2. 接口

| 接口 | 变化 |
|---|---|
| `GET /api/projects` / `GET /api/projects/{pid}` | 新增 `settings_rev`；详情新增 `copied_from`（非副本为 `null`） |
| `PATCH /api/projects/{pid}` | 可选 `base_settings_rev`；不匹配 → 409 `stale_project`，`detail.settings_rev` 为当前值；名称/规则/输出/模板变化使 `settings_rev + 1` |
| `POST /api/projects/{pid}/sources` | 登录用户上传记录 `created_by`（响应不变） |
| 收件箱 | `docs.job_finished`（发起人，每次运行一条，`dedupe=job:{jid}:{run_no}`，目标任务页）、`docs.file_rejected`（上传者，`dedupe=source:{sid}:rejected`，目标项目页） |

## 3. 明确未做

* 实时协同编辑与自动合并：无可靠合并能力，不冒充。
* 评论/提及：另一批次（需要锚点绑定版本的设计）。
* 任务的其它事件（取消由本人发起，不另通知本人；部分失败已含在 `job_finished` 的结果词里）。
