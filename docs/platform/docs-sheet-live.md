# 表格型模板的实时逐项协同（设计，分批实现）

接 [docs-collaboration.md](docs-collaboration.md) §4（CI-47）。今天表格编辑器（`SheetEditor`）只共享在场与版本帧：每人编辑
自己的私有副本、整份保存，从旧版保存时按单元格 / 字段 / 布局 / 工作表三方合并（`builtin_service.merge_sheets`），同一对象
双方都改才让人选。两个人在同一张表上**直到有人保存前都看不到对方改了什么**；持续迭代 §8.2 要求同一工作里实时看到谁改了
什么、怎么改，覆盖表格。设计由独立规划代理读代码起草（2026-09-28），这里是决定下来的版本。

## 0. 结论

* **模型：服务端定序、以稳定 id 为锚的操作**（不是 Yjs 表格文档，也不是按 A1 键的逐格操作）。浏览器先乐观应用，以服务端
  回传的补丁为准；`merge_sheets` 保留在版本边界上对账（机器 API、旧页面、单人回退、项目页字段修改）。依据：结构化对象由
  服务端权威、按属性处理（CI-46 已采用）；每条操作**应用前**按生成引擎的同一套规则校验，共享状态永远能保存、能生成；
  CRDT 会先接受无效组合再补偿，同一键的并发按 clientID 而不是时间决胜，操作者可被伪造，删除不推进状态向量（§2.1 详述）。
* **同一对象**（单元格的值与公式、字段、合并区域）：先到服务端的生效，后到的人被告知并选择「用我的值 / 保留对方的」——与
  CI-47「不静默覆盖、让人选」一致，离线重连走同一路径。**样式、行高列宽、工作表名：按属性最后写入为准，修改可见并归属到人**
  （决定：不询问）。
* **保存**：服务端在序号 N 对房间状态取快照、校验、生成 XLSX 并写成新版本（保存的是大家的实时修改，与文档编辑器一致）；
  生成任务只读版本、从不读草稿；机器 API 的整份 409 契约不变。
* **首批**：B0 先修既有缺陷（D1 已在 CI-112 修复）；B1 把今天编辑器能做的编辑变成实时逐项协同；中间插入/删除行列与公式
  引用随之移动在 B3。

## 1. 现状与读代码发现的缺陷

* 编辑器每次改动把整份快照推入撤销栈（放进共享模型后会抹掉别人的修改）；只有末尾追加行列，没有中间插入/删除；房间只用于
  在场；公式是以 `=` 开头的文本，不感知引用。
* `merge_sheets` 按工作表**名字**作键（一人改名、一人改内容被判为冲突）；不校验跨对象不变量。
* **D1（已修，CI-112）**：项目页修改内置模板字段时新版本不带编辑器模型——表格编辑器拒绝打开，文档编辑器打开空文档、正在
  进行的实时房间被清空，下次编辑器保存还原字段名。
* **D2**：`merge_sheets` 能把「A 加区域字段 B5:E7」与「B 合并 C6:D6」合并成功，随后构建报 400 `bad_editor`（区域含合并
  单元格），冲突对话框解决不了。修复：抽出纯函数 `sheet_invariants(editor)`，合并结果不满足时以 `invariant` 类冲突列出。
* **D3–D5（文档编辑器，另立项）**：重新播种没有纪元保护，带旧 Y.Doc 重连会造成内容重复；「快照」靠「操作者在房间里」启发式
  判断；房间外的保存直接替换有未保存修改的实时文档（`new_version` 不走 `_guard_live_edits`）。

## 2. 数据模型

权威状态（服务端，压缩 JSON，id 为 8 位 base36）：工作表顺序与每表的行 id、列 id 列表，非默认行高列宽，`cells`（键
`行id|列id` → `{v, t}` 原子写入），`styles`（按属性最后写入），`merges`（按 id），`fields`（锚在行列 id 上），每个对象键的
最后写入序号与人（`kseq`），每个客户端的去重序号，以及 `basis`（最近一次播种/保存时位置 → id，用于对账）。
`project(state)` 按当前位置渲染回今天的编辑器 JSON 形状；`project(seed_state(e)) == normalize(validate_editor(e))`，
不做修改就保存得到 `unchanged`。

**操作**（事务 `tx` 为原子组，例如粘贴或清空选区）：`set`/`clear`（先到者生效，带 `expect`）；`style`/`size`/`append_rows/cols`
（最后写入）；`merge`/`unmerge`、`field_add/set/move/del`（先到者生效）；`sheet_add/rename/delete/restore`（名称唯一，删除进
墓碑，保存前可恢复）——B1。`insert_rows/cols`、`delete_*`、`restore_*`——B3；移动与重排——B4。每条操作带客户端看到的
`expect`；`kseq[key].seq > expect` 且最后写入的人不是发送者时拒绝并返回 `conflict{theirs, by, at}`。

**公式**：B1 原样存 A1 文本（只在末尾追加，位置不动）。B3 改存为「文字片段 + 引用（行列 id）」，渲染时生成 A1；角落行被删
时区域收缩、单格引用变 `#REF!`，与 `engine/refshift.py`、Excel 一致；跨表引用用工作表 id，改名后自动跟随。无法解析的公式标
`raw` 并明示「插入或删除行列时不会调整」。

**不变量**（`sheet_invariants`，服务端操作校验、`merge_sheets` 结果校验、测试断言共用）：值类型与规模；字段互不重叠、单元格
字段在合并区域内须为左上角、区域字段不含合并、重复行不与纵向合并相交（与 `xlsx_add_slot` 同规则）；合并区域互不重叠、面积上限；
工作表名唯一合法；**字段锚点所在行列不可删，不可插进区域字段或重复行内部**（决定：保留这条，保护映射依赖的尺寸）；公式引用被删
的行列显示 `#REF!` 或收缩，不阻止保存。违反即拒绝，并以对方姓名说明原因（「无法把 B6 设为字段：它在 X 刚合并的 A6:B6 内」）。

## 3. 持久化与版本

* 客户端待确认队列 → 房间状态（`collab_docs`，`model='sheet'`，1 秒防抖，最后一人离开与关机时写出；落盘后发 `persisted`，
  界面才显示「已同步」）→ 版本。
* 保存路由 `POST /api/templates/{tid}/collab/save`：取 `project(state)` 与序号 N，打**显式快照标记**；线程池构建并写版本；
  `dirty` 取语义值（构建期间别人的修改仍算未保存）；内容无变化返回 `unchanged`；保存前提示包含谁的修改。
* 重启恢复：按 `head` 载入草稿，损坏回退并在 `hello` 标 `recovered`；客户端 `resume`，服务端按客户端序号去重。
* 房间外的变化（机器 API 保存、单人回退保存、项目页字段修改）：`merge_sheets(..., prefer="current")` 对账成服务端补丁，
  **外部版本在同一对象上胜出，并通知被盖掉的人、附「用我的值」**（决定）；实时草稿里的其他修改保留。
* 浏览器旧的整份 `PUT …/builtin` 在实时房间打开时返回 409 `live_room`（「请刷新进入实时协同」）（决定）；单人回退带 `solo`。
* 超过 `SHEET_LIVE_MAX_CELLS`（缺省 5 万）的模板保持 CI-47 模式。

## 4. 鉴权与安全

沿用 `collab.serve` 的握手（会话、同源 Origin、工作空间、应用资格）与每 30 秒复核；查看者只读；B2 增加写前复核（距上次复核
超过 5 秒先复核）把撤权后仍能写入的窗口压到 5 秒内；帧 2 MiB、`tx` ≤ 5000 条、单值与公式长度上限；每人每房间约 600 条/分钟
（`RateBuckets`），超出拒绝并告知稍后重发；操作者由服务端盖章；多实例用单主租约（B2），跨进程实时转发不在范围内。

## 5. 界面

他人选区画对方配色边框与姓名标签（手机显示首字），正在输入显示虚线（提示，不是锁）；刚改过的单元格按对方配色染色约 3 秒；
其他工作表有改动时标签上有圆点；读屏节流播报。顶栏「实时协同中 / 同步中（3）/ 离线：3 处修改待同步 / 单人编辑」，另示版本
状态。变更记录抽屉（B2）列出「X 修改了 结果!B2：待填 → 张三」，可按人筛选、点击跳转。「需要你处理」面板：值冲突、被拒操作
（附「复制我的值」）、被删行里自己填过的内容（「恢复该行」）。个人撤销用服务端回传的原值、带前置条件，跳过别人之后改过的单元格
并说明。手机 390 px 无横向滚动；三语言，拒绝码由客户端按 `code + detail` 组句。

`sheet_invariants == []`、投影能构建、每条被接受的操作在变更记录里恰好一次；对账）；HTTP/WS（两人不同/同一单元格、查看者、
4401/4403/4404、降级、超大帧、频率、保存期间插入的修改仍算未保存、`live_edits` 409、机器 API 与旧 PUT、重启 resume 只应用一次、
生成与复制不读草稿、超上限保持 CI-47）；前端 node（乐观应用与 Python 生成的共享语料一致、同步状态机、撤销）；浏览器

## 8. B1 第①步实现记录（`collab_sheet.py`，纯模块）

**实现时补上的决定**（设计未写明处；复审 2026-09-29 后）：操作前校验包含写出器会拒绝的内容（C0 控制符（制表/换行/回车除外）、
U+FFFE/U+FFFF、孤立代理项、超出双精度的整数，与生成器用同一判定）；新工作表名还不得为 Excel 保留的「History」，名称比较
不分大小写（与 CI-117 一致）。合并区域不覆盖有值的单元格（拒绝码 `covers_values`，列出单元格与写入者；客户端在同一 `tx`
里先清空再合并，清空照常先到者生效），值也不能写进合并区域的非左上角（`covered`）。过时的 `sheet_delete` 在他人其后写过
该表时冲突；过时的 `field_add` 不能重建他人其后删掉的字段 id。`expect` 必填，只有服务端自身的写入可用 `expect=None` 并声明
`trusted=True`。去重：每客户端记住最近 256 个序号（最新 16 个存完整结果，每个 ≤ 2 KiB），最多 64 个客户端；被遗忘的客户端
抬高 `nfloor`，房间不认识的客户端须从 `next_number` 开始编号（`hello` 下发），更早的一律 `resync`。拒绝详情只回显短字符串
与小整数，状态始终是严格 JSON。字段 id 不得是 `__proto__` 等原型属性名（已保存模型里的此类 id 用服务端键存放）；前端仍应以
`Map` / `Object.create(null)` 保存镜像。对账前先按 20 万行列 id / 20 万单元格检查外部版本，超出即 `SeedError`（房间退回
CI-47），合并后超出则整份采用外部版本；对账后至少保留一张工作表；无 id 的字段按房间内的键参与合并，不会丢失。

**已知限制**（B1 按此交付）：

* 对账沿用 `merge_sheets`：房间也改过的工作表上，外部版本的工作表顺序与缩短的行/列列表不生效（B1 中位置只增不减）；外部
  把房间编辑过的工作表改名，表现为该表被删除（保留为可恢复的墓碑并通知编辑者）加一张新名字的表。
* 每条消息为涉及的工作表建位置索引（O(行 + 列)）；合并、放置字段或写值时再建该表合并区域与字段的分块索引（O(合并 + 字段)），
  同一 `tx` 只建一次。普通表为毫秒级；有两万个合并区域的表，单次写值约 16 ms，5000 条合并的 `tx` 约 0.16 s。
* 生成器能生成、实时状态不接纳的模型在播种时拒绝，保持 CI-47：重复行字段只有 `c1` 没有 `c2`（生成器按 `c2 = 0` 读）、
  行号写成 `2.0`、超过 20 万行列 id 或 20 万单元格。

## 9. B1 第②步实现记录（房间、持久化、保存路由；`collab_sheet_room.py`）

**开关**：`SYNWEVO_SHEET_LIVE`（缺省关闭），房间打开时读取。关闭时表格房间与今天完全相同（只有在场与版本帧，`hello` 不带
`live`，101 帧被忽略，保存路由答 409 `not_live`）。打开后表格模板的房间是 `SheetRoom`：

* **打开**：房间**先登记、再读取**状态（登记期间到达的版本变化进房间队列，读完再按顺序处理；已读到的同一版本不重复处理）。
  `collab_docs` 中 `model='sheet'`（新增列；NULL 为文档房间，两者互不读取）且 `head` 等于当前版本的草稿（zlib 压缩的 JSON
  状态）直接载入；带未保存修改、停在旧版本的草稿也载入，打开后**先于**打开期间排进队列的版本把当前版本对账进去（不丢修改）；
  否则以新纪元播种 `editor_of(head)`。`SeedError`、单元格超过 `SYNWEVO_SHEET_LIVE_MAX_CELLS`（缺省 5 万）或状态超过
  `SYNWEVO_SHEET_LIVE_MAX_BYTES`（缺省 16 MiB）时房间保持 CI-47 的在场模式，`hello` 带 `live: false, live_reason`；载入的
  草稿超过这两个上限时同样处理——除非它带未保存修改（保留、照常载入，此后只接受缩小表格的修改）。草稿无法读取时记日志、
  改用 head 版本并标 `recovered`。文档房间的打开用同一顺序（同样的竞争在那里也存在，一并修复）。打开期间模板被删除：房间
  随即注销，加入者得 4404。上一个房间的收尾写入（见「持久化」）还在进行时，新房间等它写完再读草稿。
* **`hello`**：`live, epoch, seq, client, next, resumed, outcomes, persisted, content, stale_head, limits{max_tx,
  max_frame_bytes, ops_per_min, max_cells, max_bytes}`（`outcomes`：房间记得的这个客户端最近消息的结果 `{n: true | 拒绝码}`，
  `full` 同样带）。`hello` 在登记锁之外构建（入场先在锁下占位）。`client`：标签页用 `?client=` 带回自己的 id；服务端按「人/客户端」作键，别人不能
  冒用或耗掉某人的序号。**同一人带回的 id 仍被一条旧连接占着时，新连接接管它**，旧连接以 4409 `superseded` 关闭——
  服务端还没发现断线时重连的标签页，重发的消息按原号去重，不会再应用一次。带旧纪元重连仍是 4409 `stale_document`（CI-115）。
* **101 帧**（JSON，前缀变长长度，与 100 相同）：客户端发 `{type:"op", epoch, n, expect, op}`（`tx: [...]` 是
  `op: {op:"tx", ops}` 的简写；`epoch` 必填；帧里的 `client` 若有必须等于连接的）和 `{type:"sync"}`。服务端以连接的用户
  盖章 `by` 调用 `collab_sheet.apply`，给发送者 `ack{n, ok, seq, patch, before}` 或 `ack{n, ok:false, code, detail, people}`
  （`people` 为 detail 中各 `by` 的姓名与配色），给其他人 `patch{seq, patch, by}`；重复投递答原结果并标 `duplicate`。
  房间自己的拒绝码：`stale_epoch{epoch, seq}`（消息属于房间已离开的纪元：不应用、不占新纪元的序号）、`read_only`、
  `rate_limited{retry_after}` 与 `busy{retry_after}`（都不记入去重，到时按原号重发；提前重发的帧不读直接拒绝）、
  `too_large{what:"table"}`、`superseded`、`not_live`、`invalid{reason}`、`error`（模型内部故障：该组整体撤销，连接保留）。
  `resync` 之后客户端发 `sync`，得到 `full`；房间从版本重新开始时发 `reset{epoch, previous_epoch, seq, next, content}`。
* **持久化**：最后一次修改 1 秒后在工作线程压缩写出；写出后发 meta `persisted{seq, epoch}`。最后一人离开时房间在登记锁下
  当即注销，并在同一步登记为模板的**草稿待办**；锁外再做收尾写入：表格在一个独立线程里序列化、压缩、写入（不占事件循环，
  不持任何房间锁；起不了线程时就地写，不会让后来者空等），文档的小状态就地取、就地写（与以前一样要等数据库，但不在锁下）。
  房间还被占着（正在对账或重新开始）或队列里还有事（保存的标记、版本变化）时，收尾写入排在它们**之后**：最后离开的人在自己
  的事件循环上把队列跑完（原先要去的那个循环可能已随连接关闭），对账在自己的线程里完成后放开房间、接着写——写下的是它们的
  结果，而不是被它们取代的状态（第五轮复审 1：`discard_live` 重新开始期间最后一人离开，要丢弃的修改曾被收尾写入写回，下次
  打开又对账回来）；收尾写入写的是与状态同时取下的 `head` 与 `dirty`。**草稿待办是一套机制**（`CollabHub._closing`，每项
  一条，互不覆盖）：收尾写入、关闭后的更正、关闭后才标记的保存补写、版本变化删除草稿、表格离开实时模式删除草稿都在其中登记，
  无论成功、失败还是抛异常都在 `finally` 里注销并记日志（第五轮复审 3、5：更正与表格的两种后台写入曾未登记，打开者会读到
  它们之前的草稿；收尾快照抛异常时待办曾永远留着）。下一个打开者等**该模板的全部**草稿待办完成再登记、读草稿；等待在事件
  循环上轮询（不占工作线程），整个打开过程（模板的打开锁加上草稿待办）合计至多 `OPEN_WAIT_S`（25 秒，短于常见代理的超时），
  超时以 4503 `room_busy` 关闭——`y-websocket` 对 44xx 以外的关闭码按退避（至多 5 秒）重连，文档编辑器 10 秒内未同步即转入
  单人编辑已保存的版本（与以前连不上时相同）；此前是先等 60 秒、再至多 10 × 60 秒，最后以 1011 失败。守卫与变更列表读的是
  正在收尾的房间本身（不等待）；关机时等所有收尾写入。**只有登记中的房间写草稿**：
  `write_state` 先取存储的写锁，在事务里短暂持登记锁检查房间，再在锁外写行；已关闭的房间（在工作线程里对账完、或
  `live.pending` 的保存稍后才标记）不会把旧状态写到之后打开的房间的草稿上（文档房间同样），唯一例外是关闭后的更正：收尾
  写入已开始、保存的标记（或文档房间的版本变化）在那之后才到达时（之前到达的由收尾写入一并写下），房间在没有更新的房间
  登记过的前提下补写一次当前
  状态（按模板的登记代数判断），守卫不会因旧的「未保存」标记误拒；更正登记为草稿待办，写的是与状态同时取下的 `head` 与
  `dirty`，而不是写入时房间上的值。写入语句拒绝已标记删除的模板（Q19，变更记录同样）。
  **没有房间时版本变了**（钩子在提交之后运行，不等待）：由正在收尾的房间自身在那一刻的状态决定——它是带未保存修改的表格且
  没有 `discard_live` 时保留草稿（下次打开时把新版本对账进去）；房间自己的保存在它最后一人离开之后
  才写好版本（且此后没有更新的房间登记）时不动草稿：草稿是那个房间的，可能带保存快照之后输入的内容，由它的保存标记更正
  （登记代数随删除移动之后，这里若照常删除，更正会自行作废、这些内容随之丢失）。否则在登记锁下把它（以及其他仍在写的已关闭房间）标为作废、把模板的登记代数加一
  （更早关闭的房间晚到的更正因此自行作废，第五轮复审 3）、登记一个待办，锁外删除草稿行；删除在自己的事务里按这个代数检查
  （`delete_draft`），此后有更新的房间登记过就什么也不删（第五轮复审 5：被覆盖的待办晚到的删除曾删掉新房间的第一份草稿；
  现在待办互不覆盖，打开者等所有删除，代数检查是第二道保证）。
  作废的房间写草稿时在自己的事务里自查：要么它已提交、随后被删除，要么它不再写入；下一个打开者在登记时（同一把锁下）看到
  待办就先等删除完成，不会在决定与删除之间读到要删的草稿。版本号不参与这些判断（撤销会让它变小）。写入被拒时不发
  `persisted`、不改 `dirty`、不算保存。序列化时编号，较旧的一次晚到时不覆盖较新的一次。`dirty` 在每条操作后取状态记录的已改路径（O(1)），写出时在工作线程按
  投影算精确值纠正——只纠正同一基线（保存、对账、重新开始都会换基线）的状态，保存之后晚到的旧结果不会把房间重新标脏。
* **保存**：`POST /api/templates/{tid}/collab/save {note?}`（`ROUTE_POLICY` 为 write）。锁内取快照与序号 N，工作线程里投影、
  生成、`new_version(base_head=房间的版本)`（`builtin_service.save_live_sheet`，版本说明规则与编辑器保存相同），再经房间队列
  回到房间的事件循环 `mark_saved` 并广播 `head{reason:"save", saved_seq}`；构建期间别人的修改仍算未保存。投影等于 head
  版本时不写版本，返回 `unchanged`。同一房间的保存依次进行；房间自己的保存由线程局部标记识别，不当作外部版本对账；保存后
  按在线连接已声明看到的最小序号 `compact`。事件循环 30 秒内没轮到时，版本照常写好，答复带 `live.pending`，标记在循环
  轮到时完成（不再在工作线程里代做，那会因无法发帧而 500）。
* **房间外的版本**（机器 API 的 PUT、单人回退 PUT、项目页字段修改、恢复/撤销/重做）：进房间队列，`collab_sheet.reconcile`
  在**独立线程**里对状态副本完成（5 万格约 0.6–1 秒；期间房间答 `busy`，状态不变，所以副本无需加锁），对账结果超过房间的
  单元格或字节上限时按「持有不了」处理（见下条），否则回到事件循环换上新状态，
  补丁以保存者名义广播（`by`，没有人的机器凭据为 `system`，附 `outside{reason, head}`），有人的值被覆盖时广播 meta
  `overwritten{people, conflicts, by}`。
* **守卫与对账的关系（决定）**：CI-113/CI-49 的 `live_edits` 守卫照旧——房间有未保存修改时，房间外的保存、恢复、撤销、
  重做与项目页字段修改一律 409，除非 `discard_live`；守卫放行的外部版本对账进房间（id 保持）。房间里的人做单人回退保存时
  守卫按 CI-113 放行并对账——**但只在房间能持有这张表时**（`collab_sheet_room.fits`：模型自身的界限加房间的单元格与字节
  上限）；持有不了（例如远处一格超过 20 万行列 id，或超过上限）时同样 409 `live_edits`，`detail.reason: "cannot_fold"`。带 `discard_live` 且房间确有未保存修改时，房间以该版本、
  新纪元重新开始（`reset`；持有不了则退回在场模式并删除草稿，这是调用方确认过的丢弃）。**没有 `discard_live` 就不丢未保存
  的修改**：守卫之后才出现的修改（构建期间有人输入）遇到无法对账的版本（或对账出错）时，房间保留修改与原版本，广播 meta
  `live{live:true, stale:true, head}`，此后外部保存继续被守卫拦下，直到有人确认丢弃；房间干净时退回在场模式或从该版本
  重新开始，都不丢东西。
* **旧的整份 PUT**：实时房间打开时浏览器 `PUT /api/templates/{tid}/builtin` 答 409 `live_room`（`detail.online`、
  `detail.epoch`），带 `solo: true` 的单人回退保存按上面的规则处理。机器 API 的整份 PUT 契约不变；其请求体白名单漏了
  schema、SDK 与 api.md 都已有的 `discard_live`（带上即 400「不认识的字段」），一并补上。
* **鉴权与界限**：握手、每 30 秒复核、降级只读与移除关闭沿用文档房间；已打开的房间同样只对本空间开放（CI-118，4404）；
  查看者的操作答 `read_only`。帧 2 MiB（超限 4400 关闭该连接），`tx` ≤ 5000（模型答 `too_large`）。实时表格不超过
  `SYNWEVO_SHEET_LIVE_MAX_CELLS` 个单元格（`too_large{what:"cells"}`）与 `SYNWEVO_SHEET_LIVE_MAX_BYTES` 的状态：每个
  被接受的补丁按其帧长的 3 倍累加估计，每次写出草稿时换成精确值；超过时只接受清空、取消合并、删字段、删表。实测：一人以
  每条 60 × 32 000 字符连续写入，状态最多到界限加一条消息（16.6 MiB），此时每次写草稿在事件循环上序列化约 28 ms，`hello`
  约 29 ms；5 万格的表写草稿序列化约 9 ms。频率：每人每房间 `SYNWEVO_SHEET_LIVE_OPS_PER_MIN`（缺省 600）条/分钟，一条
  消息按 `max(1 + 帧长 / 64 KiB, 1 + 操作数 / 100)` 计，`sync` 按状态大小（至少 10）；**整条一次扣、被拒不扣**
  （`RateBuckets.take(key, cost)`），`retry_after` 等够即可通过；无法解析的帧同样计费。一人最多在房间里留 8 个客户端的去重
  记录：在**建立记录时**（模型的 `_record`）忘掉他自己最旧的、**没有打开的连接**的那个，只抬高他自己的序号下限（`pfloor`），
  不挤掉别人的记录，也不改变别人被告知的 `next`；打开的连接的记录从不遗忘（它还可能重发）——所以同一人第 9 个同时打开的
  可写标签页、房间第 65 个，入场时以 4429（`too_many_tabs` / `room_full`）拒绝。只数能写的连接：查看者不持有记录，不占名额
  （第五轮复审 4：查看者的标签页曾把编辑者挡在门外）；连接期间被提升为可写的查看者在提升时按同样的上限检查，超过时收到 meta
  `closed` 并以 4429 关闭。消息序号至多比该客户端的下一个号大 2^20 且小于 2^53，否则答 `resync{reason:"number_ahead",
  next}`，不应用、不记录。收尾：写草稿在事件循环上序列化约 26 ms、`hello` 约 22 ms（16.6 MiB 不可压缩的状态）；重新开始的
  `reset` 整份内容只序列化一次、所有连接共用；压缩（此规模约 0.3 s）与精确 `dirty` 都不在事件循环上。
* **加入与离开**：房间的登记、加入与最后一人离开在同一把锁下；握手期间房间被关闭（最后一人刚离开）时，新连接重新打开房间
  （从刚写出的草稿），不会落进一个没人能到达的旧房间。入场已占位、还在构建 `hello` 时模板被删除：删除不注销有占位的房间，
  占位者入场后在登记锁下复查 `gone`，以 4410 关闭（第五轮复审 2，文档房间同样），不会进入一个已删除、写入无处可去的房间。发往一个连接的帧都在该连接自己的事件循环上按顺序发出。
* **锁的顺序（全进程唯一）**：存储写锁（事务）→ 房间登记锁 `CollabHub._rooms_mu` → 房间的 `mu` → 房间队列锁；只按这个
  方向嵌套。登记锁下不做 SQL、不等其他线程、不做重活（事件循环每次加入、离开都要取它）；房间的 `mu` 下不取登记锁、不做
  SQL（离开实时模式时删除草稿交给独立线程）。模板服务在最外层事务提交后才调用 `on_template_change`（`Store.after_commit`），
  钩子不等待任何东西：此前它在事务里取登记锁，而另一个房间的草稿写入持登记锁等写锁——编辑器保存与任一房间落盘相遇即整个
  进程卡死（第三轮复审 1）。什么在哪里跑：事件循环——操作、广播、对账结果的替换、写草稿前的序列化（16.6 MiB 约 26 ms）与
  `hello`（约 22 ms）；工作线程——精确 `dirty`、压缩与写库；独立线程——对账与重新开始的播种（结果交回一个仍在服务该房间的
  事件循环，没有了就在该线程里收尾；不作为发起它的那个连接的循环上的任务——那个循环可能随连接关闭而把它取消，第五轮复审 1）、
  表格的收尾写入、离开实时模式时删草稿（在对账收尾、房间 `mu` 释放之后）、关闭后的更正与保存补写。
* **删除模板**：房间的草稿不再被最后离开的人写回，表格房间与文档房间都是（Q19，见「持久化」）；没人在的房间随删除注销。
* **回滚**：关闭开关后，未保存的表格草稿不再计入守卫与变更列表的 `dirty`，下一次版本变化时被删除。**代码回滚**到没有
  `model` 列语义的版本时，旧代码会把 `dirty=1` 的表格草稿当作文档草稿拦住外部保存（409 `live_edits`，且没有房间能保存它）；
  回滚前先让各表格保存或确认丢弃，再清掉表格草稿（先按运维流程备份）：
  `SELECT room, dirty FROM collab_docs WHERE model='sheet';` 然后 `DELETE FROM collab_docs WHERE model='sheet';`。

**给第③步（浏览器客户端）的已知限制**：

* 今天的 `SheetEditor` 不懂 101 帧：开关打开后它的整份 PUT 会得到 `live_room`。开关必须等③上线后才打开。
* 每条操作帧必须带 `epoch`；收到 `reset` 时丢弃旧纪元的待确认操作（它们会得到 `stale_epoch`）并告诉人。
* 客户端 id 放在内存里（不放 `sessionStorage`，否则「复制标签页」会让两个标签页争同一个 id：后来的接管、先来的被
  `superseded` 关闭）；断线重连带上它，待确认队列里的操作按原号重发（已处理的答 `duplicate`）。
* `busy` / `rate_limited` 按 `retry_after` 等待后原号重发；提前重发会被直接拒绝。`resync{reason:"number_ahead",
  applied:false}`：从 `detail.next` 重新编号重发。**判断一条未得到回答的消息是否已应用，只看 `outcomes`**（`hello` 与
  `full` 带，打开期间的客户端记录从不遗忘）：`true` 已应用，拒绝码为未应用（按码处理），不在其中且小于 `next` 的也未应用。
  `resync{reason:"forgotten", applied:"unknown"}` 只会发生在标签页断开期间记录被遗忘之后（`hello.resumed: false` 而本地还有
  待确认的消息）：这些消息的结果无从得知——**不可自动重发不可重复的操作**（插入行等），把它们作为「可能已应用」交给人核对；
  可重复的（写值、样式、尺寸，按 `expect`）可在 `sync` 之后按状态判断再发。
* 4429 `too_many_tabs` / `room_full`：同一人同时打开的可写标签页太多（或房间已满）；请关闭其他标签页后再打开，不要自动重连。
* 4503 `room_busy`：模板的草稿还在写入或删除，25 秒内没有完成；按退避重连即可（与 44xx 不同，`y-websocket` 缺省就会重连）。
* 非正常退出会丢掉最后约 1 秒：客户端应把操作留在待确认队列里直到 `persisted.seq` 覆盖它；重连后服务端 `seq` 小于本地时，
  以 `hello.content` 重建，未确认的操作以新的 `expect` 重发（会得到 `conflict` 或 `resync`，由人处理）。
* `hello` 带整份 `content` 且不计入频率（重连风暴时每次都发整份）；帧的先后顺序依赖单事件循环（生产部署如此）。
* 变更记录（`collab_changes`）尚未记录表格操作（B2）；`live_edits` 的 `last_by` 取自状态里最后一次由人写入的对象。
  写前复核（B2）未做：撤权后最多一个复核周期（30 秒）内仍可写入。
* `stale` 状态（版本无法对账而保留未保存修改）下房间的保存会得到 409 `stale_template`；界面应提示复制自己的内容，并由有权限
  的人确认丢弃（`discard_live`）后从当前版本重新开始。
