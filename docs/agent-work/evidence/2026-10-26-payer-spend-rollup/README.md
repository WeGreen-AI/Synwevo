# 个人支出汇总基准（成本容量第二阶段，2026-10-26；本机隔离临时库）

由 [`scripts/bench_cost_admission.py`](../../../../scripts/bench_cost_admission.py) `--sizes '' --wallet-sizes 200000,1000000` 生成：每个规模在系统临时目录新建一个
隔离的 Store（拒绝 `data/`、配置的 `SYNWEVO_DATA_DIR` 与已有库），结束后删除；合成的夹具价目、用户与钱包，没有网络、密钥或真实价格。
工作负载（每个规模 N）：**一个钱包**，2034-05-01T00:00（周一）至 2034-05-20T12:00（周六）之间 N 次已结算调用（按产品的顺序写入：账本分录、结算、
再改调用状态；金额随机 1–1000），外加 300 个仍预留的调用；个人日、周、月上限已启用。

- **检查**：`PayerBudgets.check(amount=1)` 在 `BEGIN IMMEDIATE` 内，200 次取样。读一次故障探测、当期最多 31 个日行（这里 20 个）与仍预留调用的索引；
  20 万与 100 万已结算调用时相同，不随结算量增长。
- **触发器（实时）**：每次结算的三条产品写入（账本分录、结算、调用状态）自成一个 `BEGIN IMMEDIATE … COMMIT`（`synchronous=FULL`），在本库与一份
  删掉四个个人支出触发器的副本上交替执行，取差值。一次结算只更新它那一天的一个日行，所以远低于第一阶段每对 300 µs 的量级。
- **回填**：一次重放全部已结算调用（只在首次启用、触发器版本变化、日行表/哨兵/标记丢失时运行，持有写锁）。
- **校验**按风险监控的调用方式（`mode=daily` 从上月 1 日起，这里是全部历史；`mode=recent` 两天）在子进程里运行，峰值是该子进程的最大常驻内存
  （含解释器与导入约 100 MB）；每日校验除了逐日比较，还把读取结果与无上限的对照计算（`reference_exposure`）比较，后者也读该钱包的结算历史。
  时间随读到的已结算调用线性增长，内存不增长。

附录 §9 目标：检查 p95 ≤ 1 ms 且 1M 不超过 200k 的 1.5 倍；触发器 ≤ 150 µs/次结算；回填与校验时间记录在案。各文件 `wallet_targets_met` 逐项给出，
两个规模、两个 Python 版本全部达标。`query_plans` 是检查里每条语句的 EXPLAIN QUERY PLAN：全部是主键或索引 SEARCH
（`payer_spend_days` 主键、`billing_calls_holds`、故障索引、账户与上限版本的主键），不读结算、账本分录或 `billing_calls_payer_period`。

重现：`python scripts/bench_cost_admission.py --sizes '' --wallet-sizes 200000,1000000 --out <文件>`（`--work` 可指定临时目录的父目录）。
