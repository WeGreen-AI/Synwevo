# 身份、信任边界与权限矩阵

本文件是授权实现的**契约**：代码、测试与评审都以此为准。写在这里的每一条都必须有对应的服务端
强制点和测试；没有实现的不写进来，实现了但没测的标注为「未验证」。

状态：**账户、组织与管理员 API 台本机交付（2026-09-25）**。
本轮用户明确替代旧的 API UI 禁令：只允许平台管理员的 `api_platform.manage` 使用控制台和管理接口；
组织/空间角色不授予该权利。控制台权利不包含业务数据权利，签发和执行仍须当前有效的空间批准、
资源及 scope 交集。普通 Docs 业务 API 不改为管理员专用。本轮实现、正负验收与未覆盖条件统一记录在 handoff，不把历史测试数字当作本轮结果。
本轮不部署、不访问 VPS、不修改 DNS；测试邮件使用隔离本地接收设施。

| 管理员分阶段认证 | 管理能力看**会话**的认证强度，不只看账户角色：`sessions.admin_capable(amr)`。`email`、`idp:<id>`、`passkey`（无本人验证）是一因素，`/api/auth/me.permissions=[]`、`admin_locked=true`，`/api/admin/*` 与 API 台管理接口一律 `403 step_up_required`；账户页口令确认（`/api/auth/reauth`）把 `password` 追加到 `amr` 后解锁，页面切换不重复挑战。登录页不按邮箱是否为管理员改变形状；不因个别管理员未绑定 TOTP 隐藏其他人的登录方式。`test_session_strength.py`、`test_email_code_login.py`、`test_external_identity.py`。 |
| 账户内改口令 | `POST /api/auth/password {current_password, new_password}`：当前口令按重认证限流校验，新口令按策略校验；本会话保留，其他会话与全部令牌立即失效，重置链接与 MFA 票据作废，发安全通知并写审计/撤权日志。无口令账户（仅外部登录）通过邮箱重置链接设置口令。 |
| 外部身份提供商 | 只按 `(provider, subject)` 关联，不凭邮箱合并；已验证邮箱匹配现有账户时只生成关联要约，须口令（+第二因素）确认。关联/解除关联需 `mfa` 作用域 strict 重认证；不能移除最后一种登录方式。未配置凭据的提供商不显示；配置不完整则拒绝启动。管理员可读的配置状态 `GET /api/admin/identity-providers` 只含回调地址、scopes、发行者、客户端 id 前 8 位、密钥是否存在、缺失变量名——不含秘密，也没有写入口（`test_identity_provider_status.py`）。 |
| 账户页返回目标 | `/api/auth/me.return_targets` 由服务端列出（配置的门户 + `Apps.apps_for` 当前可打开的应用的 `/auth/start` 入口）；账户页只按 `from=<id>` 在列表中选择，不接受 URL、不读 Referer，账户源无开放重定向。`test_return_targets.py`。 |
| 备份恢复 | 组织撤权采用写前落盘日志及恢复 receipt，日志写入失败时不提交组织变更。恢复重放冻结/删除/降权/成员移除/批准撤销，不能复活新备份后的权限或自动发送旧邮件。撤销历史数据的指派同样写前落盘（`workspace_unclaimed`，每次恢复都重放、按条目自身时间应用，不撤掉之后的重新指派；写不进日志则不撤销），见 §3.3。 |

## 0. 出发点：现状有什么、没有什么

改造前（HEAD `164cfba`）的真实情况，由代码核实：

| 项 | 现状 |
|---|---|
| 身份 | **没有用户概念**。`ui_users` 只是一张共享口令表，所有人登录后看到同一份数据 |
| 会话 | **没有**。HTTP Basic 每请求重发凭据，因此没有登出、没有会话列表、没有撤销、没有重新认证 |
| 授权 | **没有**。任何通过 Basic 的人对全部项目有完全权限 |
| 数据归属 | `projects` / `templates` / `jobs` 有 `tenant` 列，但**全部是 `'default'`**；`projects` 没有 owner 列 |
| 机器接口 | `/api/v1*` 需要 API 密钥，密钥带 `tenant` 与 `scopes`，是目前唯一真实的作用域机制 |
| 匿名面 | `SYNWEVO_UI_AUTH=none` 时 `/api/*`（非 v1）、SPA 与静态资源**完全匿名** |

所以这不是「给已有权限系统加角色」，而是**在一个单租户应用上从零引入身份与授权**，同时不能弄丢
已有数据，也不能破坏已交付的文档引擎与 `/api/v1` 契约。

## 1. 信任边界与数据流

```
                    ┌─ 不可信 ─────────────────────────────────────┐
  浏览器 ──────────►│ Cloudflare / 反向代理（可伪造头，见 §2）      │
                    └────────────────┬─────────────────────────────┘
                                     │  HTTP（源站只监听回环）
                    ┌────────────────▼─────────────────────────────┐
                    │ FastAPI 单进程                                │
                    │  _gate 中间件：身份 → 工作空间 → 限流          │
   信任边界 ①───────┤  services / views：逐对象授权                 │
                    │  job-runner 线程：请求之外，需自带身份上下文   │
                    │  webhook 线程：出站，受 SSRF 限制              │
                    └───┬─────────────┬──────────────┬─────────────┘
                        │             │              │
   信任边界 ②──────► SQLite       blob 存储      子进程（LibreOffice /
                     （WAL）      （内容寻址）    Tesseract / PDF）
                                                  ▲ 处理不可信文件，
                                                    必须限权限/网络/资源
```

* **边界 ①**：请求进入进程。此处确定「调用者是谁、属于哪个工作空间、有哪些权限」。
  之后**一律不再相信客户端传来的 `user_id` / `tenant_id` / `role`**。
* **边界 ②**：进程访问持久化。此处不做授权判断——授权必须在 ① 之后、访问 ② 之前完成，
  否则 job-runner 这类非请求路径会绕过。
* **子进程边界**：解析器处理的是攻击者可控的文件，按不可信代码对待（§7）。

## 2. 反向代理与转发头

本轮仅在本机回环运行，没有部署或建立隧道。历史部署可能存在反向代理；适用规则是：

* `X-Forwarded-For` / `X-Forwarded-Proto` / `X-Forwarded-Host` **只有在明确配置了可信代理时才采信**。
  限流与审计里的来源 IP 必须走同一套判定，不能一处信一处不信。
* 目前签名下载链接的域名取 `SYNWEVO_PUBLIC_URL`，否则才回落到转发头（`api/v1.py:public_base`）。
  伪造这些头只能改到攻击者自己拿到的 URL，令牌仍独立校验。

## 3. 身份种类

| 种类 | 载体 | 生命周期 | 用途 |
|---|---|---|---|
| 用户会话 | 服务端会话 + `HttpOnly` Cookie | 空闲过期 + 绝对过期，可即时撤销 | 浏览器里的一切操作 |
| 机器身份（API 密钥） | `Authorization: Bearer dw_…` | 长期，可撤销/轮换，带作用域 | `/api/v1` 自动化 |
| 签名链接 | URL 中的短期签名凭据（有效期内可重用） | 短期（默认 15 分钟），每次重验签发者权限 | 下载单个产物/压缩包 |
| 引导令牌 | 一次性 CLI 产物 | 单次 + 短有效期 | 建立首位平台管理员 |

**机器身份的权限 = 密钥作用域 ∩ 该身份当前权限**。密钥不继承管理权限，也不因为「密钥还在」
而绕过账户停用。

### 3.1 平台身份：中央会话与应用会话是两件事

账户服务是 OIDC Provider，Synwevo Workspace和 Synwevo Docs 是各自独立的客户端。因此会话有三层，三层分别
管理，任何一层都不是另一层的副本：

| 层 | 在哪里 | Cookie 作用域 | 结束方式 |
|---|---|---|---|
| 中央认证会话 | 账户服务 | host-only，账户服务域名 | 平台登出、全设备撤销、账户停用 |
| 应用会话（门户 / Synwevo Docs 各一份） | 各应用自己 | host-only，各自域名 | 应用内退出、后通道登出、令牌撤销 |
| 令牌（access / refresh） | 只在服务端之间 | 不进浏览器 | 撤销、过期、刷新时重新核验 |

* **不共享宽域 Cookie，不复制中央会话值，不开放任意跨域请求。**「登录过」变成「这里也算登录」，
  只能靠走完协议。
* **不同端口不隔离 Cookie。** Cookie 按主机划分作用域并忽略端口，所以本机验证使用
  `accounts.localhost` / `portal.localhost` / `docweave.localhost` 三个主机名，
  `scripts/verify_sso.py` 用真实的 `http.cookiejar` 把这件事量出来而不是假设。
* 浏览器不保存访问令牌、刷新令牌或机器密钥；前端包里不出现客户端密钥。
* **ID Token 不是 API 凭证。** 它在回调里验一次（签名、`iss`、`aud`、`nonce`、有效期），验完丢弃。
* `auth_time` 和 `amr` 随授权码传递，并写进应用会话的 `reauth_at`。「平台登录过」**不等于**
  刚刚重认证——两小时前的中央认证不能让危险操作免除 reauth。

### 3.2 应用资格是独立的一层

`app_id`、`client_id`、API audience、`workspace_id` 是四个不同的概念，不得互相代用。

登录成功只确认身份。能不能使用某个应用，由三个条件**同时**决定：应用本身启用、该工作空间启用了
它、该用户在该空间有资格（或应用策略为 `members` 且他是成员）。

* 授权端点在发码前检查资格；应用回调在建会话前**再检查一次**，因为两者之间资格可能已被撤销。
* 刷新令牌时再检查一次账户状态与资格——这才是短期访问令牌的意义所在。
* 将来新增的应用**不会**因为某人是 Synwevo Docs 的空间管理员而自动可用。
* Synwevo Workspace不在应用注册表里：注册表列的是「可以被授予或拒绝的业务应用」，而门户是去看自己有哪些
  应用的地方。把它放进注册表，会让它出现在自己的首页上，也会让「没有门户资格」变成一个人连自己的
  账户设置都打不开的状态。任何有效账户都能进门户，包括还不属于任何工作空间的人——他看到真实空状态，
  **不是** `default` 空间。

### 3.3 历史数据认领

尚未认领的历史 `default` 空间为 `legacy / pending_claim / 0 成员`；已经合法认领的空间保留现状，
不会在启动或迁移时重置。注册、平台管理员初始化、应用接入和首次登录都不会自动认领它。
待认领且没有成员时无人获得读取权，**包括平台管理员**。

认领只能由平台管理员经 `POST /api/admin/workspaces/{wid}/claim` 完成，并且：

* 需要 `platform.workspaces.claim`，只有最高管理员持有（B1-2 复审，2026-09-29 本地）：认领把全部历史文档交给
  一个账户，是业务内容的交付，不是「冻结」那样的停止开关；
* 目标**不能是操作者本人**（409 `self_claim`），也**不能是持有任何平台授予的账户**
  （409 `target_is_platform_admin`），在认领的事务内检查：平台权限从来不是读取文档的途径，对谁都一样；

* 目标必须是**已经存在**的账户；这一步不创建账户；
* 需要**带作用域的近期重认证**（`scope=admin`，且 `strict`——刚登录不算，必须为这件事重新输入口令）；
* 需要**书面理由**，原样写入审计；
* 在**一个事务**里完成成员关系、空间状态、应用启用与使用资格；
* **不改写任何一行业务数据**（项目仍带 `tenant='default'`，因为 workspace id 就是 tenant 值）；
* 只作用于指定的这个空间，**不顺带授予平台管理权**，也不给管理员自己任何读取权。

认领的审计记录（`admin.workspace.claim`）与认领在**同一事务**写入，并记下认领前后的名称
（`name_before` / `name_after`），撤销时据此判断名称是否仍是认领设置的那一个。

**撤销指派**（`POST /api/admin/workspaces/{wid}/unclaim`，`{"reason", "expected_members"?}`）是认领的
反向操作，规则与认领相同：只有有效平台管理员、`scope=admin` 的 strict 近期重认证、书面理由（8–500 字）；
组织或空间角色（包括这个空间的所有者本人）一律 404。只接受 `kind='legacy'`、不属于组织、未删除、
`status` 为 `active` 或 `frozen` 的空间；待认领时答「没有指派给任何人」。**冻结的指派直接撤销**，冻结随之
结束：发现指派错了的管理员通常先冻结（停止开关），此前的「先解冻再撤销」会在两步之间把数据重新交给被错误
指派的账户（评审发现，Q21）。所有条件在写事务内重新判断，所以并发的认领、撤销或冻结不会留下半个状态
（两个撤销同时提交：一个成功，另一个得到「没有指派」；撤销与冻结同时提交，结果总是待认领）。
一个事务内：

* 删除该空间的**全部**成员关系（不只是认领时指定的账户，之后被邀请加入的人也一样）；
* 按「移除成员」的方式收回使用资格：每位成员写一行显式的 revoked（`members` 策略下「没有行」表示允许），
  空间里其余仍有效的资格行一并撤销；
* 删除该空间的应用启用（未指派的空间没有应用）；撤回尚未接受的邀请；
* 撤销在该空间里行事的全部平台令牌（人的与服务账户的，原因 `workspace_unclaimed`），未兑换的登录码作废；
* 状态回到 `pending_claim`；名称只有在**仍是认领设置的那个**时才改回生成的「历史数据（待认领）」，
  管理员之后（或认领之前）自己起的名字保留；
* 审计 `admin.workspace.unclaim`：操作者、理由、被移除的成员（ID、邮箱、角色）、撤回的邀请数与令牌数、
  停用的应用、之前的名称与状态、指派时间与指派人、不受影响的运维密钥数与会停止的任务数，以及
  `journaled: true`。

**安全日志写在提交之前**：上面这些改动开始之前，同一事务里先向安全日志追加一条 `workspace_unclaimed`
（只有空间 ID 与「名称是否改回」，写盘并 fsync），与组织撤权一样是写前落盘。于是不存在「已经提交、
却还没写进日志」的时刻——进程在提交与日志之间退出、或备份恰好取在日志与提交之间，从更早的备份恢复都
会重放这次撤销。这条记录**每次恢复都重放**（不按备份时间筛），并按它自己的时间「截至当时」应用：只移除
当时已有的成员关系、启用、资格、邀请、令牌和登录码，只有在之后没有人再被指派（空间行没有更新、没有
成员留下）时才把状态改回 `pending_claim`——所以它永远不会撤掉之后的重新指派。日志写不进去（磁盘满、
权限错）时**撤销不执行**，什么都不改变，答 503 `journal_unavailable`（三种语言的句子），并写一条
`result="error"` 的审计；需要立即停止访问时先冻结（冻结不依赖日志写入成功），日志恢复后再撤销。

**不删除任何数据**：项目、模板、来源文件、任务、结果与文件都原样保留，在再次指派之前**任何账户**都不能
读取，包括平台管理员（运维签发的 `dw_` 密钥是例外，见下）。会话不需要处理：成员关系在每次请求时重新
核验，会话里指向已不属于自己的空间会在下一次请求时被清除。浏览器标签页若仍在 `X-Synwevo-Workspace` 里
带着这个空间，请求会被拒绝（`workspace_context_invalid`）直到重新选择——把历史数据指派给自己的管理员
重新登录后正是这种标签页（新会话从最早加入的空间开始，也就是历史数据），所以概览在撤销成功后，若本
标签页的上下文就是这个空间，会先丢掉它再刷新。已经打开的实时编辑连接（模板协作房间）在**下一个**读取
或写入帧就被关闭（4403 `membership_ended`），不等 30 秒的周期复核；只听不发的连接由周期复核关闭。
排队或运行中、由成员、委托、服务账户或经审批的密钥提交的生成任务，会被执行器按提交者重新授权时取消
剩余样本（`authorization_revoked:workspace_unavailable`，与冻结或移除成员时一样），已生成的结果保留，
再次指派之后需要手动重新运行；运维 `dw_` 密钥提交的任务继续。

被移除的人收到与「被移出空间」相同的站内通知与即时邮件（`member.removed`，三种语言），执行者写作
「平台管理员」（`actor_kind`），不写管理员的邮箱或姓名——平台管理员的身份从不交给空间成员，而被错误
指派的账户可能是陌生人；执行撤销的管理员若本人是成员则不通知自己。

机器凭据沿用**已有**规则，不另起一套：服务账户要求空间处于 active 且启用了 Synwevo Docs
（`Apps.check_access_for_workspace`），所以撤销后它的令牌已被撤销、也换不到新令牌，但注册本身不删除、
不停用；经审批签发的 API 凭据只在批准人仍是该空间当前所有者时有效（`Approvals.require_owner`），
所以撤销后立即被拒，审批记录保持 `approved` 而不是被标为撤回——与冻结空间或移除所有者时完全一样，
因此再次指派给同一位所有者时，他当初的批准重新生效（指派给别人则不会），确认对话框也这样写明。
运维签发、没有审批绑定的 `dw_` 旧密钥按待认领空间的既有规则（`MachineAuth._legacy_key`）照常可用，
与指派之前相同；预览数出它们（`operator_keys`），确认对话框把它们写成例外，而不是说「没有人能打开」。

再次认领时，认领写入的使用资格记录的是**这次认领**的时间与管理员（撤销为每位前成员写过一行 revoked，
此前重新认领只清空 `revoked_at`，`granted_at` / `granted_by` 仍是撤销时的时间和执行撤销的管理员）；
认领的时间在拿到写锁之后才取，排在它之前提交的撤销的日志时间之后。

只读预览 `GET /api/admin/workspaces/{wid}/unclaim-preview`（平台管理员即可，不需要重认证，无副作用）
返回：将失去访问的每个人（邮箱、显示名、角色）、将撤回的邀请数与仍可使用的令牌数、服务账户与有效
审批数、不受影响的运维密钥数（`operator_keys`，按 lineage 计）、会被停止的排队或运行中任务数
（`jobs_stopping`）、项目与模板**数量**（不含名称）、当前名称与撤销后的名称、指派时间与指派人（取自
最近一条 `admin.workspace.claim`）。账户服务「平台管理 → 概览」在历史数据已指派（含冻结）时显示
「历史数据已指派」卡片和「撤销指派」按钮；确认对话框列出预览里的每个人，并把这份名单作为
`expected_members` 发给服务端——名单在确认之后发生变化时服务端拒绝（`assignment_changed`），对话框就地
刷新名单再请确认。撤销成功后焦点移到结果提示上（它所在的 `role=status` 区域从页面加载起就在，刷新期间
也不卸载），因为打开对话框的按钮已随卡片替换而消失。

`strict` 这一条是本轮新增的。此前只有一个重认证作用域（硬编码 `"mfa"`），而一次新登录会写入
空作用域并满足所有检查——于是「为添加 Passkey 而证明身份」同时解锁了管理操作，「刚登录的管理员」
则根本看不到确认提示。现在作用域是一个封闭集合（`mfa` / `admin`），且危险操作要求作用域**完全相等**。

### 3.4 机器身份

`/api/v1` 接受三种凭据，全部经 `machine.py` 解析成同一个 principal 形状：

| 凭据 | 主体 | 租户来源 | 权限 |
|---|---|---|---|
| `dw_<id>_<secret>`（兼容保留） | 密钥本身 | 密钥登记的 tenant | 密钥的 scopes |
| 服务账户访问令牌 | 客户端自己 | 客户端登记的 workspace | 登记的 `api_scopes` ∩ 本次申请 |
| 用户委托访问令牌 | 授权它的那个人 | **每次调用重新解析**的成员关系 | 客户端许可 ∩ 当前角色 ∩ 本次授权 |

* **不复用用户口令、中央登录 Cookie 或 ID Token。** 只带身份范围（`openid`/`profile`/`email`）
  的令牌调用业务接口会被 403 拒绝。
* **每次调用重新核验**账户状态、成员关系、应用资格。令牌记录的是当初授予了什么，不是现在还
  成不成立；固化进令牌就是「已撤权的人继续工作到过期」。
* **当前角色会收窄委托**：签发时是 editor、现在是 viewer，则写被拒、读仍可，令牌本身不需要撤销。
* 服务账户有**独立生命周期**：有人退出浏览器、撤销自己的全部会话，都不影响它；停用该应用或
  该工作空间则立即影响它。
* 机器凭据可经受控 CLI 与平台管理员 API 台管理。组织/空间角色不授予 `api_platform.manage`；
  控制台签发还需空间所有者的当前批准，不能凭平台管理权读取业务数据。

### 3.5 Passkey / WebAuthn

认证器在**中央账户服务**管理。RP ID 由 `SYNWEVO_RP_ID` 配置，默认取发行者域名，**绝不从请求
的 Host 推导**——那会让任何能访问到服务的人以自己选的名字登记凭据。可信 origin 是一份精确列表
（`SYNWEVO_RP_ORIGINS`），不是「RP ID 下的任意来源」，否则 origin 校验就无事可做。

* **注册挑战与登录挑战严格分开**（`webauthn_challenges.purpose`），互不满足；均服务端保存、
  单次使用、由条件 UPDATE 保证。
* **登记与删除需要 `scope=mfa` 且 strict 的近期重认证**：刚登录不算。增加或删除一种登录方式，
  正是提示本身有意义的场合；能被静默跳过的确认等于没有确认。
* **「账户有 Passkey」≠「这次登录验证了本人」**。`amr` 记录实际发生的事：`passkey_uv` 表示
  这次仪式里认证器验证了本人（PIN / 指纹），`passkey` 表示只证明了持有。需要抗钓鱼**且**已验证
  本人的策略查前者。
* **凭据绑定域名**。改域名不会迁移已登记的 Passkey：它们在新域名下根本不存在，必须重新登记。
  每个凭据记录自己的 `rp_id`，界面上直接显示「域名已变更，无法使用」，而不是让它悄悄消失。
* **签名计数器由 WebAuthn 库严格校验**：已存或本次计数任一大于 0 时，本次计数必须大于已存值；
  倒退或重复返回 `401 bad_assertion`，不会签发新会话，也不会更新凭据计数。两者均为 0 时允许继续
  其余验证，以支持不维护计数器的认证器。签名、challenge、origin、RP ID 和用户在场校验仍然执行，
  不能为了兼容某个设备而关闭这些检查。拒绝本身不能证明凭据已被克隆；设备计数异常需单独排查。
* **只存公钥材料**。私钥永远不离开认证器。
* 删除最后一种登录方式会被拒绝（口令已清除且只剩一个 Passkey 时），而不是弹个确认框让人点掉。
* 登录端点**不接受邮箱**：由浏览器选择可发现凭据，服务端从断言得知是谁。为某个邮箱返回凭据列表
  会顺带回答「这个邮箱有没有账户」。

**验证范围**：`services/identity/tests/test_passkeys.py` 使用明确标记的软件测试认证器，以真实 P-256
密钥签署 clientData / authenticatorData，覆盖计数倒退、重复和双零计数等服务端校验。
本轮还在隔离合成数据上用真实 Chrome 浏览器与 CDP 虚拟 CTAP2 认证器验证了登记、改名、
可发现凭据的用户验证登录（`passkey_uv`）和删除。虚拟认证器的用户验证是测试模拟，**不代表已验证
物理安全密钥、指纹、面容或跨设备同步的互操作**；本轮未触发物理认证器或采集生物特征。

### 3.6 找回口令与邮箱验证

* **请求重置对任何地址都给同一个答复**，页面文案也一样。否则这就是一个无需认证的账户存在性探测器。
  未命中的地址同样写入审计（`result=denied`），所以对这个端点的扫描在日志里看得见。
* **邮件发送失败也不改变答复**。`mailer.enqueue` 故意在未配置邮件时抛 503——发不出去的邀请不是
  邀请——但在这个端点上，响应形状本身就是安全属性：让 503 透出去，会变成「有账户的地址 503、
  没账户的地址 200」，把唯一为防枚举而设计的端点变成完美的枚举工具。这里**只在这里**吞掉它，
  并以 `result=error` 大声记进审计。
* **链接不是动作**。打开链接只读取令牌（`GET /api/auth/reset/preview`），消费需要第二次、
  明确的 POST。邮件安全扫描器会跟随链接；被扫描器一次 GET 消耗掉的令牌，等于一次当事人没申请、
  之后也做不成的重置。
* 令牌短时（重置 2 小时、验证 24 小时）、单次使用、**只存摘要**；重新申请会让上一封邮件里的链接
  立刻失效。
* **重置不等于登录**。它设置口令并结束全部会话与平台令牌，然后请人正常登录——因此第二因素照常生效。
  在这里直接签发会话，会让「我忘了口令」成为绕过当事人自己 MFA 的通道。
* 重置**不会**关闭第二因素、不会改邮箱、不会解除停用。已停用的账户走不完这个流程。
* 完成后向本人发出安全提醒；提醒失败不会回滚重置。
* 审计里不出现令牌原文或口令。

**验证范围**：本地 `SYNWEVO_MAIL_MODE=file` 与合成 localhost TLS 接收器验证业务及故障路径；
这些设施不能代替真实投递证据。2026-09-24 通过隔离账户的真实 HTTP 邀请/邮箱验证链路向唯一授权地址
发送两封，mailcow 及 SMTP2GO 接受记录见 [部署记录](../quality/deployment.md)。
收件箱可见性单独记录，不从 SMTP 接受推断。

当前 SMTP 边界：固定服务器配置的 From/envelope sender；STARTTLS 或隐式 TLS 必选其一，使用系统
信任库验证证书与主机名后才认证。仅账户进程接收邮箱密码。业务请求只入队，worker 原子领取，最多 8 次
有限重试；DATA 确认丢失或崩溃遗留领取标记时停止自动重发并报告 `delivery_unknown`。
日志/错误不包含密码、SMTP 原始响应或邮件正文；配置冲突中的秘密值也脱敏。详见
[账户邮件运维](../operations.md#6-账户邮件仅发信)，回归在 `services/identity/tests/test_mail_transport.py`。

### 3.7 Webhook 的出站请求

Webhook 是本服务**主动向外发起**的请求，因此它的风险方向与其它接口相反：不是"谁能进来"，而是
"我们会替调用者去连哪里"。

* **签名**：工作空间订阅使用 `webhook-id`、`webhook-timestamp`、`webhook-signature`，对原始请求体及
  `<id>.<timestamp>.` 前缀签名。有效签名也可能被重放，接收方仍须检查时间窗口和事件 ID 去重。
  部署级回调额外保留兼容头 `X-DocWeave-*`。实现、轮换及真实接收器见 [API 规范](../integration/api.md#4-事件与-webhook)。
* **默认 https**，`http` 需要显式 `SYNWEVO_DOCS_WEBHOOK_ALLOW_HTTP=1`。
* **不跟随跳转**：一个 302 可以把已经通过检查的目标换成任意地址。
* **内网地址默认拒绝**，例外必须写进 `SYNWEVO_DOCS_WEBHOOK_ALLOW_PRIVATE`。
* **校验过的地址就是实际连接的地址**（`resolve_checked` 返回地址列表，连接固定到其中之一）。
  这一条是本轮补的：此前 `check_url` 解析一次做判断，urllib 连接时**再解析一次**——一个由对方
  控制的域名可以先回一个公网地址通过检查，再回 `169.254.169.254` 或 `127.0.0.1` 让请求真正发过去。
  两次解析之间的那个窗口，让整个检查失去意义。固定地址的同时保留 SNI 与证书校验，不因此削弱 TLS。
* **不使用环境里的代理**。`build_opener` 默认会装上按环境变量配置的 `ProxyHandler`；代理既会把
  带签名的事件正文送到无人选择的地方，又会自己做一次解析，从而绕过上面的地址校验。
* 重试有限次且退避递增；失败记录在 `webhook_deliveries.last_error`，不吞掉。
* Webhook 可经受控 CLI、受限机器 API 与平台管理员 API 台管理；控制台调用同一业务 API，
  使用明确选定的受限凭据，并保留当前授权、SSRF、签名与有限重试规则。

## 4. 权限矩阵

权限以稳定标识符表示（不是可自由输入的表达式）。角色是权限集合的命名快照。

### 4.1 平台级（委派平台权限，schema v27，2026-09-29 本地交付）

平台管理不再是一个 `platform_role='admin'` 标志，而是**权限目录 + 内置角色 + 授予记录**
（`synwevo_core/platform_access.py`）。有效平台权限 = 该账户全部计入的授予所含权限的并集，每个请求重新读取。

| 内置角色 | 权限 | 明确不可以 |
|---|---|---|
| `super_admin` 最高管理员 | 目录中的全部权限（按定义；新登记的权限自动属于它） | **不获得任何工作空间内文档正文的读取权** |
| `access_admin` 账户与访问管理员 | 概览；账户查看/停用恢复/支持；空间查看/冻结解冻；组织查看/自有组织生命周期；配置查看；邮件查看/重试；应用运行记录查看；审计；管理员名册 | 授予或撤销任何平台角色；指派历史数据；修改注册策略；API 管理 |
| `support` 支持 | 概览；账户查看；找回邮件与结束会话；空间、组织、邮件、应用运行记录查看 | 停用账户；任何修改配置或空间状态的操作 |
| `auditor` 审计查看 | 概览、账户、空间、组织、配置、邮件、应用运行记录、审计、管理员名册的只读 | 任何写操作 |
| `api_platform_admin` API 平台管理员 | 概览；`api_platform.manage` | 账户、空间与配置管理 |
| `finance` 财务 | 概览；`platform.billing.view`（充值、赠送、拒付、未用余额，只含金额与元数据）；`platform.billing.manage`（支付设置与密钥、带理由赠送、解除拒付冻结） | 账户、空间、组织、模型配置管理；任何业务内容 |

权限 ID：`platform.overview.view`、`platform.users.view|manage|support`、`platform.workspaces.view|manage|claim`、
`platform.orgs.view|manage`、`platform.config.view|manage`、`platform.mail.view|manage`、`platform.apps.view`、
`platform.audit.view`、`platform.roles.view|assign|assign_super`、`api_platform.manage`、
`platform.billing.view|manage`（org-payments：资金只属于最高管理员与财务角色，见 docs/platform/wallet-payments.md §4）。与草案（admin-coverage.md §3.1）相比新增
`platform.orgs.manage`（组织生命周期路由是写操作，不能挂在只读权限上）和 `platform.workspaces.claim`
（指派历史数据是业务内容的交付，只属于最高管理员；`.manage` 只剩冻结与解冻），理由写在模块文档里。

`platform.apps.view` 读「应用运行」「流程运行」两页（`synwevo_identity/admin_runs.py`，五个只读路由），由已能读邮件投递的
三个角色与最高管理员持有，`api_platform_admin` 不持有。这两页只显示运行的元数据——哪个操作、状态、时间、错误代码、入口、
账户与空间——其中包括个人 Agent 操作的操作名与时间，但从不显示对话正文，也不显示任何输入、输出、失败说明或用户起的名称。
授权拒绝（403）与输入校验失败（422）发生在运行行建立之前，不留下运行行，所以页面上的「失败」只统计处理过程中的失败。

强制点与规则：

* **同一个请求检查** `require_platform(request, permission)`：所有 `/api/admin` 路由与 `/admin` 外壳都经过它，
  API 控制台经 `require_manage`（查 `api_platform.manage`）。顺序：无会话 401 → 账户不可用 401 →
  **没有任何平台权限 404（与不存在的页面同形；组织 owner、空间 admin 也是 404）** → 有其他平台权限但缺这一项
  403 `platform_permission_denied`（写审计 `admin.access.denied`，同一操作者同一权限每 60 秒最多一条）→
  一因素会话 403 `step_up_required` → 危险操作未严格重认证 403 `reauth_required`。
  「没有任何平台权限」在请求闸门（`core/http.py`）里、路由之前就判定：参数或请求体校验（422）、不支持的方法（405）
  与不存在的路径对这些账户都是同一个 404，校验错误不再回显角色目录。
* **低权限管理员不能对高权限管理员下手**：结束会话、发找回邮件、重试其邮件、恢复账户时，若目标的有效授予
  （不论当前是否计入）含有操作者没有的权限，403 `target_outranks_actor`，写审计（同一操作者同一目标每 60 秒一条）。
  停用本身已拒绝任何持有授予的账户（`demote_first`）。**恢复只作用于 `suspended` 账户**（409 `not_suspended`），
  不能让待验证或正在删除的账户变为 active。
* **谁计入**：账户 active、未删除、不是应用身份、邮箱已验证。例外：主机权限下的授予（`migration:v27`、
  `bootstrap:web`、`bootstrap:cli`）不要求邮箱已验证——引导创建的首位管理员从未验证过邮箱，要求它会在迁移时
  把唯一的管理员锁在外面。
* **持有 ≠ 可授予**：授予/撤销需要 `platform.roles.assign`，涉及 `super_admin` 还需 `assign_super`；操作者还必须
  持有该角色的每一项权限。**任何人不能给自己授予或撤销带授权能力的角色**（403 `self_assignment`）。
* **被授予者前置条件**（关闭 D2）：active、邮箱已验证、不是应用身份、能完成管理员身份确认
  （有口令、可做用户验证的 Passkey 或已启用 TOTP，与 `sessions.admin_capable` 接受的方式一致）；
  否则 409 `target_pending` / `target_unavailable` / `target_unverified` / `application_identity` /
  `target_cannot_step_up`。
* **至少一名可用的最高管理员**（可用 = 计入、能完成身份确认，**并能完成严格重认证**——D10 之前即有口令；
  只有 Passkey 或 TOTP 的最高管理员能看全部页面却改不了任何东西，不计入；Passkey 只计绑定当前 RP ID 的）：
  撤销、停用、本人删除会让可用最高管理员归零时 409 `last_super_admin`；检查与写入在同一个 `BEGIN IMMEDIATE`
  事务内，两人同时互相撤销只成功一个。`super_admin` 只授予有口令的账户（409 `target_cannot_reauth`）。
  口令不能从账户上移除，所以移除 Passkey 或关闭 TOTP 不会让人失去「可用」，无需检查（D10 之后需要）。
  持有任何平台授予的账户不能被直接停用（409 `demote_first`）。最高管理员授予不设期限。
* **生效与失效**：授予时把被授予者现有的中央会话收紧到管理员闲置时限（`SYNWEVO_ADMIN_IDLE_S`）并取消保持登录；
  撤销在对方的下一个请求生效（权限每个请求重读）；到期的委派授予不再计入。
* **审计**：`admin.platform.grant` / `admin.platform.revoke` 在同一事务内写入，含前后角色集合（有效授予，不论是否
  计入）、理由与请求 ID；替换到期授予时记下被替换的授予。系统结束授予也写 `admin.platform.revoke`：账户删除到期
  （`system:account_deleted`）与安全日志重放的删除（`system:journal_replay`，与 `platform_role='none'` 同一事务）。
  系统自己写的理由是固定句子（`platform_access.SYSTEM_REASONS`），页面按读者语言显示。
* **回滚镜像**：`users.platform_role` 保留，值为 `admin` 当且仅当存在有效的 `super_admin` 授予，否则 `none`，
  与每次授予变更同一事务写入。只有委派角色的管理员镜像为 `none`：回到上一版本时他们失去权限而不是变宽。
  `Store` 每次打开时对账：上一版本在回滚期间对该列的升降会被带入授予；遗留的 `operator` 变为 `none` 并写审计。
* **撤销恢复保护（2026-09-30，本地待部署）**：显式撤权先写 `platform_grant_revoked` 安全日志，再与事务收据一起提交。
  恢复按实际授予标识撤权，兼容 v26 镜像迁移，保留后续合法重新授予；重放使已有可用最高管理员归零时拒绝恢复，不能复活已撤身份；原本未初始化的备份仍可恢复。
  旧恢复工具不认识新日志种类，必须保留兼容读取器；代码回滚与数据恢复分开处理。
  无日志恢复不能重建平台授权撤销，目前尚缺待核对门禁，不能据“全部退出登录”宣称权限已安全恢复。
  操作与版本边界见 [管理员恢复说明](../platform/admin-operations.md)。

平台权限**不是**工作空间权限的超集。没有任何平台角色带业务内容权限；没有临时「支持访问」产品流程，
也没有代登录。业务文档访问必须通过该空间的真实成员关系、应用资格与读/写/导出权限检查。
「平台运维」（`operator`）从未带有任何能力（D17），v27 迁移为无平台权限，并从所有选择器中移除。

页面（`acweb/governance/access.ts`）只提供调用者权限够得着的操作：不可用的写操作显示为禁用并写明原因，
概览里的「指派历史数据」只对能指派且能搜索账户的人显示；服务器仍逐个请求裁决。

### 4.1.1 组织级权限目录与自定义角色（2026-09-26，CI-23）

组织的三档基础角色（owner / admin / member）映射到一个稳定的权限目录（`synwevo_core.org_roles.CATALOGUE`），组织拥有者可以
把可委派权限组合成自定义角色并分配给成员；有效权限 = 基础角色集合 ∪ 已分配角色。组织级检查（设置、成员、空间、邀请）按权限
判定；交接所有权与组织生命周期仍只有基础 owner 能做，且不能放进任何角色。委派不越权：创建、修改、分配角色都要求操作者已持有
其中每一项权限并持有 `org.roles.manage`。组织级权限**不改变**工作空间与文档的授权（下一节四档角色与 `authz.py` 不变）。
细节见 `docs/platform/organization-roles.md`。

### 4.2 工作空间级

| 角色 | 读 | 写 | 运行任务 | 下载/导出 | 管成员 | 生命周期 |
|---|---|---|---|---|---|---|
| 只读成员 | ✓ | ✗ | ✗ | 按单独权限 | ✗ | ✗ |
| 编辑成员 | ✓ | ✓ | ✓ | ✓ | ✗ | ✗ |
| 空间管理员 | ✓ | ✓ | ✓ | ✓ | ✓ | ✗ |
| 空间所有者 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓（需重新认证） |

* 空间管理员**不能**授予平台权限，**不能**访问其他空间。
* 「下载/导出」与「读」分开：只读成员能看预览不等于能把文件带走。
* 最后一名所有者受保护，不能被移除/降级到无人拥有。

### 4.3 授权的默认

* **默认拒绝**。没有明确匹配的规则即拒绝。
* 工作空间由**可信认证上下文 + 当前有效成员关系**确定，不由请求参数确定。
* 每一次读/写/删/关联/导出/下载都做**对象级**判断，批量操作**逐个**判断。

## 5. 必须覆盖的旁路

引入授权时最容易漏掉的不是主表，而是派生物。下列每一项都要有授权，且缓存键必须包含身份/空间：

原文件 · 工作副本 · 解析结果 · OCR 文本 · 缩略图 · 页面图 · 预览产物 · 搜索与自动补全 ·
错误详情 · 统计计数 · 任务事件流 · 产物下载 · ZIP 打包 · 结果清单 CSV · 签名链接 ·
blob id 直取接口 · 临时文件 · 日志导出

### 5.1 历史越权清单（修复前证据，非当前行为）

旧记录的路由数量口径不一致，不用作当前接口清单；当前清单由运行路由和 OpenAPI 契约测试核对。
下表来自早期 FastAPI TestClient 双租户测试的历史结果：这些端点在修复前对
另一个租户的对象上返回了 200 和真实内容。兄弟端点（`/api/projects/{pid}`、`/api/jobs/{jid}`、
`/api/artifacts/{aid}`）返回 404，说明检查是**手工逐个写的、漏了一半**。

| 端点 | 拿到什么 |
|---|---|
| `GET /api/projects/{pid}/sources` | 他人项目的完整文件清单，含 `sha256` |
| `GET /api/sources/{sid}/view` | 文档本体（表格单元格 / docx 块 / PDF 元数据 / 幻灯片） |
| `GET /api/sources/{sid}/download` | 原始上传字节 |
| `GET /api/sources/{sid}/search?q=` | 全文命中与上下文 |
| `GET /api/sources/{sid}/page/{n}.png` | 渲染页面图（且是**唯一**设了 `private, max-age=600` 而非 `no-store` 的路由） |
| `GET /api/sources/{sid}/words/{n}` | 每个词及其坐标，等于整页转写 |
| `GET /api/jobs/{jid}/items`、`/report.csv` | 逐样本结果与清单 |
| `GET /api/preview-files/{blob}`、`/view`、`/page/{n}.png` | 存储里的任意字节 |
| `GET /api/desensitized/{blob}` | 同上（名字是装饰性的） |
| `GET /api/projects/{pid}/locate?file={sid}` | 用自己的映射去解析**他人**文档，返回逐字段取值 |
| `DELETE /api/sources/{sid}`、`PUT .../options`、`POST .../ocr` 等 | 修改/删除他人项目的文件 |

**当时的结构缺陷：blob 层没有授权。** 当时 `views.preview_file(blob)` 只问「这个 sha256
在磁盘上存在吗」，四条路由直接暴露它；而 blob id 本身在普通响应里就发出去了（每个来源文件行和
每个产物行都带 `sha256`），既不过期也不回收，产品里任何「删除」都不会让它失效（生产代码从未设置
`artifacts.deleted_at`，项目/来源/模板删除都是软标记）。

> 因此：**任何只给项目加空间过滤、却把这五条 raw-id 路由留在外面的方案，设计上就是可绕过的。**
> 授权必须落在取数据的那一层，而不只是列表查询的 `WHERE` 里。

### 5.3 健康检查契约（已修正）

`/healthz`、`/readyz` 是精确匹配的匿名探针。前者只给 `status`，明确测试实例额外给测试标记；
后者返回组件级就绪状态，不暴露版本、schema、环境或文件路径。就绪探针不写业务行，存储探测在
数据根目录而非 blob 树。`/api/health` 仍受普通 UI 认证规则约束。实际实现位于 `synwevo_core.http.install_probes`。

`/api/about` 与 `/api/source-code`（本程序的许可与 AGPL-3.0 第 13 条的对应源代码）同样是精确匹配的
匿名路径（`SOURCE_OFFER_PATHS`），在每个角色、每种认证模式下都不要求登录：第 13 条要求向**所有**通过网络
与程序交互的用户提供源代码，包括只用到登录页、公开站点或工作空间的人。两个处理函数都不读取任何工作空间
数据；压缩包按客户端限速（每分钟 6 次；IPv4 按地址，IPv6 按 /64），带匹配 ETag 的重新验证返回 304 且不计数。
相邻路径（`/api/about/`、`/api/source-code/x`）不因此匿名。压缩包只含源代码发布清单上的文件（镜像构建时
从 `git archive` 上下文写入的清单，或检出的 `git ls-files`），两者都没有时拒绝（503），不会遍历目录。

网关的每个判断——角色拒绝、精确匿名路径（探针与上面两个）、各前缀——都基于路由实际匹配的路径
（ASGI `scope["path"]`，`synwevo_core.http.routed_path`），不基于 `request.url.path`：后者由 Starlette 从
scope 重新拼接再拆分，请求目标里百分号编码的 `?` 或 `#` 被解码进路径后会在那里截断，`/api/about%3F/x`
读成 `/api/about`，而路由匹配的是 `/api/about?/x`，豁免就落到了另一条路由上。编码变体（`%3F`、`%3f`、`%23`，
含探针在 `basic` 模式下）见 `tests/integration/test_source_offer.py`。

## 6. 任务快照与撤权

任务在提交时固定**数据与配置版本**（已实现），但**不固定权限**。必须在以下时点用执行身份的
**当前**资格重新判定：排队转运行、重试、崩溃恢复、访问关键资源、发布产物。

| 事件 | 对运行中任务 | 对已产出产物 |
|---|---|---|
| 成员被移出空间 | 停止新执行 | 该身份不再可访问 |
| 账户停用 | 停止新执行 | 不可访问 |
| 空间冻结 | 停止新执行 | 按冻结策略 |
| 机器密钥吊销 | 停止新执行 | 该密钥签发的链接失效 |

取消时记录「已完成」与「未完成」范围，避免半成品对外发布。

## 7. 文档处理隔离

解析器处理攻击者可控文件，按不可信代码对待：限制文件系统可见范围、网络、CPU/内存/时长；
每任务独立临时目录并在成功/失败/取消/崩溃后清理；不把数据库凭据或主密钥暴露给解析进程。
已实现的公式计算保留，但外部工作簿/网络引用、宏、DDE、PDF 脚本不得自动执行或联网。

**接纳先于解析（2026-09-25，CI-20）。** 所有上传入口（工作台、机器 API、分片上传、服务器路径导入、模板）
汇聚到同一个接纳函数：配置了扫描器时字节先进入 `scanning`，引擎判定干净才交给解析器；命中签名的行变为
`rejected` 且 blob 被删除，同样的字节再上传直接拒绝；引擎不可达或文件超过扫描上限的行停在 `scan_failed`，
不解析、不预览、不下载，也不因为"没检出"而放行。下载与内容接口在授权之后再检查接纳状态（409/410），
所以隔离结论不改变逐空间授权，也不向无权用户泄露文件是否存在。平台管理员能看到聚合的拒绝计数，
看不到被拒文件的内容——字节已经不在了。细节见 `file-acceptance.md`。

## 8. 审计

敏感变更记录：操作者（用户或机器身份）、空间、当时权限范围、动作、对象、结果、时间、请求 ID。
**不记录**密码、令牌、TOTP 种子、恢复码、文档正文。审计写入与被审计的操作保持事务一致；
审计通道故障时按风险拒绝或持久排队，不静默丢弃。普通管理员没有改写/删除审计的入口——
但同库的一张可写表**不等于**不可篡改日志，本文件不做这种声称。

### 9.1 口令参数（实测，非抄默认值）

在部署机 vultr_tokyo（3 vCPU，与另外四套生产服务共用，容器上限 3 GiB）实测：

| 方案 | 中位 | p95 | 取舍 |
|---|---|---|---|
| 19 MiB t=2 p=1 | 27.6ms | 38.4ms | OWASP 当前下限 |
| 39 MiB t=2 p=1 | 77.6ms | 78.9ms | |
| **46 MiB t=2 p=1** | **96.4ms** | **100.8ms** | **采用** |
| 64 MiB t=3 p=4 | 84.2ms | 86.8ms | argon2-cffi 默认，**因 p=4 被否** |
| 64 MiB t=3 p=1 | 178.4ms | 202.6ms | 登录体感偏慢 |

否决库默认值的理由是 **p=4**：在 3 vCPU 且跑着别人生产服务的机器上，每次哈希起四个线程，
登录高峰会和那些服务抢 CPU。p=1 让并发由信号量控制而不是由调度器决定。
选 46 MiB 是 OWASP 内存下限的 2.4 倍、单线程、约 100ms。内存才是真正的预算：
峰值 = 并发数 × 46 MiB，信号量设 4 即约 184 MiB，不会把内存从文档生成那边抢走。
参数写在 PHC 串里，日后调高可在下次成功登录时自动升级旧哈希，无需导出任何明文。

### 9.1.1 邮件与令牌

* 邮件先进 `mail_outbox`，由工作线程发送并带退避重试。**端点只回「已排队」**，真实结果随后可查——
  内联发送要么阻塞在慢 SMTP 上，要么在还没有结果时就宣称成功。失败的行**保留**在库里，
  不为了让界面好看而删掉。
* 未配置 SMTP 时模式是 `disabled`，入队直接报错；**不会出现「已发送」而其实什么都没寄出**。
  `file` 模式把 .eml 写到本地供开发验证，每封都带 `LOCAL FILE SINK` 抬头，无法误认为真实投递。
* 邮件里的链接一律用 `SYNWEVO_PUBLIC_URL` 拼。若取请求 Host，任何能访问服务的人都能让邀请邮件
  指向自己控制的主机，而令牌在真实主机上依然有效。
* **打开链接不完成任何动作**：链接只到落地页（只读 preview），接受需要一次显式 POST。
  邮件安全扫描器和链接预览机器人会自动抓 URL，在 GET 上动作等于把接受邀请的能力交给它们。
* 令牌只存 SHA-256、短期、单次；同类型新令牌作废旧令牌，所以收件箱里的旧重置链接会立即失效。
* 邀请绑定**空间 + 邮箱 + 角色 + 邀请人**，四者任一在事后失效都会让邀请失效：
  过期、撤销、被新邀请取代、空间不可用、**邀请人被降级或停用**（在接受时重新校验，不只在签发时）。
  不能邀请高于自己的角色；平台管理员不因平台身份获得任何空间的邀请权。
* 已有账户的邮箱必须先登录再接受，否则邀请就成了替陌生人设置口令的途径；
  以**另一个**账户登录时接受会被拒绝并指明该邀请发给谁——这正是"同事浏览器没退出"的场景。
* 无法投递时邀请会被**撤回**，而不是留下一条没人收得到的链接。

### 9.1.2 第二因素

* **TOTP 种子加密落地**（AES-256-GCM，`cryptography`）。但密钥在哪里决定了这层加密值多少：
  设了 `SYNWEVO_SECRET` 时密钥来自环境，与数据真正分离；否则回落到库内 `meta.server_secret`，
  **一份数据库副本即可同时拿到密文和密钥**。这一点不静默——`manage.py info` 直接打印当前是哪一种。
  即便在回落配置下 MFA 仍然完成它的主要职责（防的是口令泄露，而不是数据库失窃），但差别真实存在。
* 密钥用 HMAC 从根密钥派生并做域分隔，不与签名下载链接共用同一个值。
* **开始设置 ≠ 已启用**：必须先验证一个真实验证码才算启用，否则等于用一个没人证明能读到的密钥把人锁在外面。
* **防重放**：每个时间步最多接受一次（`last_step` 单调递增）。因此**确认启用时用掉的那个码无法再用于登录**，
  这是刻意的。容差为前后各一步。
* 启用 TOTP 时**立刻**签发 10 个恢复码——MFA 开始生效的那一刻，丢手机也开始要紧了。
  恢复码只存哈希、单次使用、重新生成即作废旧的全部；比对时忽略大小写、空格与连字符（人是照纸抄的）。
* **登录变成两步**：口令正确只换到一张短期一次性 ticket（独立表，不放 `sessions`——
  任何放进 `sessions` 的东西都离"被当成已认证会话"只有一个 bug 的距离）。
  ticket 五分钟过期、单次、**五次错码即作废**，六位数验证码无法在窗口内被穷举。
* **关闭 MFA 的保护不弱于开启**：需要近期重认证**并且**输入一个当前有效的验证码——
  拿到你没锁屏的笔记本的人，不该在没有第二因素本体的情况下把第二因素摘掉。
* 再认证记录在服务端**且带作用域**：为 MFA 做的验证不会顺带解锁删除工作空间。
  刚登录算作"近期已认证"（与 sudo 模式一致），但久置的会话不算。

### 9.2 会话与再认证的具体语义

* Cookie 是不透明随机值，库里只存它的 SHA-256 —— 备份或支持导出拿到 `sessions` 表也**无法重放为登录**。
* 两个时钟都在**每次读取时**强制：空闲（默认 12h，管理会话 1h）与绝对（默认 30 天）。
  空闲期可续，绝对期永不延长，所以被窃 cookie 的寿命有上界。
* 再认证 `reauth_at` 记在**服务端**并且**带作用域**：为添加 Passkey 做的验证不会顺带解锁删除工作空间。
* CSRF 用 double-submit，与 CORS 无关（CORS 管谁能读响应，拦不住跨站把请求**发出去**）。
* SameSite 取 `Lax` 而非 `Strict`：Strict 会让验证邮件、邀请邮件里的链接在首次跳转时不带 Cookie，
  用户点了「确认」却落到登录页。Lax 仍然不把 Cookie 交给跨站 POST，其余由 CSRF 校验兜住。
* 会话列表只报 User-Agent 能诚实支持的信息，**不声称地理位置**：用 IP 猜城市再当事实展示，
  在用户正要判断「这是不是我」的时候比不显示更糟。未知就是「未知设备」。
